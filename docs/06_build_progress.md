## 세션 메모리 (2026-09-21 추가)

논문 3.4절의 `MemorySaver`를 실제로 붙였다. 같은 대화 안에서 분쟁 대상이 다음 턴으로 넘어간다.

- 대화 ID(`conversationId`)가 LangGraph `thread_id`다. 첫 질문 때 서버가 발급하고 화면이 다음 질문에 실어 보낸다
- **이어받는 것은 `DisputeTarget`(품목·분쟁 유형)뿐이다.** 대화 전체를 프롬프트에 붙이지 않는다 (논문 3.4)
- 이어받은 품목은 검색 질의에도 얹는다. 없으면 "그럼 환불은요?" 같은 후속 질문이 엉뚱한 표를 찾는다
- **장기 기억은 두지 않는다.** 체크포인트는 프로세스 메모리에만 있고, `새 대화`를 누르거나 서버가 내려가면 사라진다
  (논문 9.3이 스스로 적은 한계를 그대로 따른다)
- Vanilla·Native는 논문의 대조군이므로 상태를 갖지 않는다
- 메모리 상한: 대화 500개 / 마지막 사용 후 120분 (`SESSION_MAX`, `SESSION_TTL_MIN`)

| 턴 | 질문 | 추적된 분쟁 대상 | 검색 질의 | 결과 |

| 1 | 인터넷으로 산 노트북이 한 달 만에 고장 났어요 | 노트북 · 제품 고장 | (그대로) | 전자제품·사무용기기 |

## Native RAG 주입 방식 (2026-09-21 변경)

논문 부록 4-B는 "검색된 기준을 **정제 없이 전량** 프롬프트에 주입"한다. 그대로 바꿨다.

- `NATIVE_MODE=paper` (기본): 질의 확장·그래프·리랭킹 없이 벡터 상위 20개를 그대로 주입
- `NATIVE_MODE=compressed`: 이전 방식(하이브리드 검색 + 리랭킹 상위 5개)
- 실측(Luna, 노트북 질문): 전량 주입 20개 = 1,731 입력 토큰. 논문의 10,091과 차이가 나는 것은 **청크 크기** 때문이다
  (논문 500자 / 우리는 표의 한 행)

### 품목 매칭을 위해 추가한 것 (논문에 없는 부분)

별표Ⅱ는 품목이 달라도 문구가 거의 같아서(`ㅇ 계약취소` 수준) 벡터 검색만으로는 품목이 구분되지 않았다. 그래서 두 가지를 더했다.

1. **질의 확장**: 별표Ⅰ(대상품목) 매핑 + `config/synonyms.yaml`(일상어 → 고시 용어). 예: 노트북 → 퍼스널컴퓨터·전자제품·사무용기기
2. **품목 한정 검색**: 질문에서 품목이 특정되면 그 품목 표 안에서 한 번 더 검색해 RRF에 한 축으로 얹음 (임베딩 재사용이라 추가 비용 없음)

## 구축 중 고친 것

파싱 단계에서 자동 검증이 실제 데이터 손실을 여러 번 잡았다.

1. 한 쪽에 표가 여러 개일 때 제목이 뒤섞이던 문제 → 표마다 제목을 따로 찾음
2. 분쟁유형이 두 줄일 때 둘째 줄이 버려지던 문제
3. 줄 끝 숫자가 표 테두리를 넘어가 잘리던 문제
4. 품목 제목이 표 안 첫 줄에 있는 경우를 놓쳐 표가 쪼개지던 문제 (전자제품 표가 p14/p15로 갈라져 있었음)
5. 청크 ID 중복 (같은 조문 번호가 두 번 실린 경우)

검증 규칙도 손봤다.

- 해결기준 마커 개수 불일치는 **경고**로 (한 행에 해결기준이 둘 이상 붙는 표가 실제로 있음)
- 숫자 비교는 단위를 떼고 숫자만 (`24`와 `24시간`이 줄바꿈 때문에 다르게 잡히던 문제)

그 밖에 고친 것:

- **Critic 재시도 횟수가 세어지지 않아 5회까지 돌던 버그** → 검증 횟수를 따로 세도록 수정
- **그래프가 옛 청크 ID를 가리키던 문제** → 현재 청크에 없는 ID는 버리고 다시 추출
- 임베딩을 **증분 갱신**으로 (파싱을 고칠 때마다 전체 비용을 내지 않도록)
- 로그 저장을 DB 종류에 기대지 않게 (`merge` 사용) → 로컬은 SQLite, 운영은 Neon
