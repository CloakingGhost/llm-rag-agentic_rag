## 1. 문제: 표가 어떻게 깨지는가

별표 Ⅱ(품목별 해결기준, 8~141쪽)의 표는 **열 구분선만 있고 행 구분선이 없습니다.** 분쟁유형 10개가 있어도 PDF 안에서는 "분쟁유형 칸 1개 / 해결기준 칸 1개 / 비고 칸 1개"로 되어 있고, 줄바꿈으로만 행이 나뉩니다.

| 추출 방식 | 결과 | 문제 |
|---|---|---|
| `extract_text` (이전 구현) | 한 줄에 세 열이 섞임: `1) 법정대리인의 동의 없는 미성년자 계약 ㅇ 계약취소 * 기 납부한 요금(가입비…` | 어떤 해결기준이 어떤 분쟁유형에 대응하는지 사라짐. Native RAG가 이 청크를 읽고 '허위·과장광고' 기준을 잘못 적용함 (Notion 테스트 케이스 1) |
| `extract_tables` | 열은 정확히 나뉘지만, 각 열의 모든 행이 셀 1개에 뭉침 | 행 대응을 복원해야 함 |

그래도 복원할 단서가 있습니다. **같은 행의 분쟁유형과 해결기준은 같은 높이(y 좌표)에서 시작합니다.** 분쟁유형에는 계층 마커(`1)` → `①` → `-` → `ㆍ`)가, 해결기준에는 항목 마커(`ㅇ`, `o`)가 붙어 있습니다.

## 2. 별표별 구조

| 별표 | 쪽 | 구조 | 난점 |
|---|---|---|---|
| Ⅰ 대상품목 | 2~7 | 번호 \| 업종 \| 품종 \| 해당품목. 행 구분선 있음 | 한 셀 안에서 품종과 해당품목이 줄 단위로 짝지어짐 (란류 ↔ 계란, 메추리알 등) |
| Ⅱ 품목별 해결기준 | 8~141 | 분쟁유형 \| 해결기준 \| 비고. **행 구분선 없음** | 행 복원, 여러 쪽에 걸친 표 병합 (`⑤자동차 (2-1)`, `(2-2)`), 업종 그룹 제목 (`<⑥이동통신서비스업>`), 3열이 아닌 표(위약금표·환급률표 등) |
| Ⅲ 품질보증·부품보유기간 | 142~144 | 품목 \| 품질보증기간 \| 부품보유기간. 행 구분선 있음 | 비교적 깨끗함 |
| Ⅳ 내용연수표 | 145 | 품목 \| 내용연수. 세로 병합 셀 | 병합 셀의 값을 아래 행으로 채워야 함 |

전체 표 177개 중 3열 표가 153개이고, 130개에 병합 셀이 있습니다.

## 3. 파싱 방안 → **C(규칙 + LLM 보정)로 결정** (2026-09-19)

| 안 | 방식 | 장점 | 단점 |
|---|---|---|---|
| A. 규칙 기반 | 단어 좌표로 열을 나누고, 마커와 y 좌표로 행을 복원 | 비용 0, 결과가 매번 같음 | 해결기준 하나가 여러 하위 행에 걸쳐 세로 가운데 정렬된 표에서 오류 발생 |
| B. LLM 전면 구조화 | 모든 표를 gpt-4o-mini로 JSON 변환 | 불규칙한 표에도 유연함 | 숫자·기간을 잘못 옮길(환각) 위험. 실행할 때마다 결과가 다를 수 있음 |
| **C. 규칙 + LLM 보정 (결정)** | A로 1차 파싱 → 자동 검증 → **실패한 표만** LLM이 재구성 → 다시 자동 검증 | A의 정확성과 B의 유연성을 모두 얻음. 원문 보존 검증으로 LLM 환각을 막음 | 파이프라인 단계가 하나 늘어남 |

C안에서 섞는 것은 **좌표 계산 코드(규칙)**와 **LLM 보정**입니다. 논문의 '하이브리드 검색'(벡터 + 그래프)과는 관계가 없습니다.

```text
표 177개 ─▶ [규칙 파서] ─▶ [자동 검증 V1~V6] ─통과─▶ 지식베이스
                                   │
                                  실패
                                   ▼
                     [LLM 보정: 행 짝만 다시 맞춤] ─▶ [자동 검증] ─통과─▶ 지식베이스
                                                          │
                                                         실패 ─▶ 표 전체를 청크 1개로 + 실패 목록에 기록
```

C안에서 LLM에 넘기는 입력은 `extract_tables`로 **열이 이미 나뉜 텍스트**입니다. LLM은 행 대응만 다시 맞추면 되므로, 새 내용을 만들어낼 여지가 적습니다. LLM 비용은 운영자 키로 1회 발생하며, gpt-4o-mini 기준 1달러 미만으로 추정합니다.

### 프로토타입 결과 (A안)

| 쪽 | 표 | 결과 |
|---|---|---|
| 48 | 이동통신서비스업 | **9개 행 모두 정확히 복원**. 계층(`3) 통화품질 불량` → `- 가입 14일 이내` → `ㅇ 계약해제`)과 비고 6개가 분리됨 |
| 20 | 자동차 (2-1) | 일부 실패. 해결기준 `o 차량교환 또는 필수제비용을 포함한 구입가 환급`이 하위 3행에 걸쳐 있어서 행이 쪼개짐. 마커 `o`가 옆 열로 넘어감(`안o 전도`) → **자동 검증으로 실패를 감지할 수 있는 유형** |

## 4. 청크 설계

**행 1개 = 청크 1개**로 만들고, 상위 경로를 본문에 포함합니다. 표 전체는 부모 문서로 따로 보관합니다(parent-child 방식).

```text
[소비자분쟁해결기준 별표Ⅱ > 이동통신서비스업]
분쟁유형: 주생활지에서의 통화품질 불량 > 가입 15일 이후 6개월 이내
해결기준: 위약금 및 할인반환금 없이 계약해지 및 해지신청 직전 1개월 기본료 50% 감면 / 통화품질개선
비고: 통화품질불량은 주생활지에서 엔지니어가 측정하여 확인함. …
```

| 별표 | 청크 단위 | 메타데이터 |
|---|---|---|
| Ⅰ | 품종 1개 (업종 경로 포함) | 업종, 품종, 해당품목 목록 |
| Ⅱ | 분쟁유형 말단 행 1개 | 업종, 품목, 분쟁유형 경로, 쪽 번호, 부모 표 ID |
| Ⅱ 비고 | 표에 붙은 비고 전체 | 부모 표 ID (행과 함께 제공) |
| Ⅲ | 품목 1개 | 품목, 품질보증기간, 부품보유기간 |
| Ⅳ | 품목 1개 (병합 값 채움) | 품목, 내용연수 |
| 전자상거래법 | 조문 1개 (길면 항 단위) | 장, 조 번호, 조 제목 |

검색은 행 청크로 하고, LLM에는 행과 함께 **부모 표의 비고**를 넘깁니다. 비고에 기간·예외 조건이 몰려 있기 때문입니다.

### 임베딩 텍스트는 따로 만든다 (2026-09-20 추가)

실측 결과 별표Ⅱ 행의 해결기준은 **중앙값 17자, 81%가 30자 미만**입니다(`ㅇ 계약취소` 수준). 이 텍스트를 그대로 임베딩하면 품목이 다른 행들의 벡터가 거의 같아져 검색이 무너집니다. 그래서 **임베딩에 넣는 텍스트와 화면에 보여주는 텍스트를 분리**합니다.

| 용도 | 내용 |
|---|---|
| 임베딩 텍스트 | 경로 + 분쟁유형 + 해결기준 + 비고(600자로 자름). 실측 중앙값 237자 |
| 메타데이터 | `path`, 업종, 품목, 분쟁유형 경로, 해결기준 원문, 비고, 쪽 번호, 표 ID |
| 화면 표시 | 메타데이터의 `path`와 해결기준 원문 |

근거와 수치는 [data_feasibility.md](data_feasibility.md) §2를 참고하십시오.

## 5. 자동 검증 항목

사람 검수 없이 진행하기로 했으므로, 아래 검증을 통과한 표만 지식베이스에 넣습니다.

| # | 검증 | 기준 | 잡아내는 오류 |
|---|---|---|---|
| V1 | 문자 보존율 | 표 영역 원문 글자 수 대비 출력 글자 수 (공백 제외) ≥ 99% | 누락, 중복 |
| V2 | 숫자·단위 일치 | 원문의 숫자 토큰 집합(`2년`, `4만㎞`, `50%`, `10배`)과 출력의 숫자 토큰 집합이 같음 | **LLM이 숫자를 바꾸는 환각** |
| V3 | 마커 개수 | 해결기준 마커(`ㅇ`, `o`) 수 = 출력 해결기준 항목 수 | 행 쪼개짐, 합쳐짐 |
| V4 | 고아 행 없음 | 해결기준이 없는 말단 분쟁유형, 마커 없이 시작하는 해결기준이 없음 | 세로 가운데 정렬로 인한 어긋남 |
| V5 | 연속 표 병합 | `(2-1)`, `(2-2)` 같은 분할 표가 모두 합쳐짐 | 페이지 경계 누락 |
| V6 | 품목 커버리지 | 별표 Ⅱ의 품목 제목이 모두 결과에 있음 | 표 전체 누락 |

V1~V4를 통과하지 못한 표는 LLM 재구성으로 보냅니다. 재구성 후에도 실패하면 그 표는 **표 전체를 청크 1개로** 넣고 실패 목록에 기록합니다. 표를 버리지 않으면서, 깨진 행 대응을 만들어 넣지도 않기 위해서입니다.

## 6. 그래프 구축

### 6-1. "그래프를 새로 만든다"의 의미

논문의 하이브리드 검색은 두 경로로 문서를 찾습니다.

| 경로 | 찾는 방식 | 강점 |
|---|---|---|
| 벡터 검색 | 질문과 **문장 의미가 비슷한** 청크 | 표현이 달라도 찾음 |
| 그래프 검색 | 질문에 나온 **개념과 연결된** 청크 | 표현이 달라도 관계로 이어진 근거를 찾음 |

그래프는 "개념(노드)과 관계(엣지)"로 된 지도이고, 각 노드는 그 개념이 나오는 청크를 가리킵니다.

```text
질문: "스마트폰 산 지 2주 만에 고장 났는데 교환되나요?"
  → 질문에서 개념 추출: [스마트폰, 고장, 교환]
  → 그래프에서 '스마트폰' 노드를 찾고 이웃을 따라감
      스마트폰 ─해결기준→ [별표Ⅱ 스마트폰 > 정상 사용 중 성능·기능 하자 > 제품 교환 또는 구입가 환급]
      스마트폰 ─보증기간→ [별표Ⅲ 스마트폰 품질보증기간]
  → 벡터 검색 결과와 RRF로 합침
```

벡터 검색만 쓰면 다른 품목 표의 '교환' 문장이 더 비슷하다고 나올 수 있습니다. 그래프는 **'스마트폰'에 해당하는 행을 확실히 끌어오는 역할**을 합니다. 논문이 말한 "벡터 단독 시 상위 법조문 40% 누락"을 메우는 부분입니다.

### 6-2. 이전 구현의 문제

Notion 테스트 5건에서 질문이 달라도 그래프는 **항상 청크 0~4번을 반환**했습니다. 이 청크들은 고시의 개정 이력과 부칙입니다("개정 2005.10.1. 재정경제부 고시…"). 그래프가 문서 앞부분 20개 정도의 청크로만 만들어진 것으로 보입니다. 결과적으로 그래프 검색은 근거를 보태지 못하고 **잡음만 섞었습니다.**

"새로 만든다"는 것은 **지식베이스 전체(전자상거래법 전 조문 + 별표 Ⅰ~Ⅳ 전체 행)를 대상으로 그래프를 다시 구축한다**는 뜻입니다.

### 6-3. 구축 방안 → **G1(논문 방식)으로 결정**

**결정 (2026-09-19)**: 문제가 있더라도 논문 방식으로 먼저 진행합니다. G2·G3는 개선 조치 항목으로 옮겼습니다([improvement_actions.md](improvement_actions.md) IMP-01).

G1로 가더라도 이전 구현의 버그(문서 앞부분 약 20개 청크로만 구축)는 고쳐야 합니다. **지식베이스 전체 청크에서 개념·관계를 추출**합니다. 청크는 대략 1,500개로 추정하며, gpt-4o-mini 기준 비용은 1달러 미만으로 예상합니다(운영자 부담).

아래는 검토했던 비교표입니다.

| 안 | 방식 | 장점 | 단점 |
|---|---|---|---|
| **G1. 논문 방식 (결정)** | 모든 청크에서 LLM이 개념·관계를 추출 → NetworkX + Louvain 군집 | 논문 서술과 같음 | 추출 결과가 매번 다름. 청크 수만큼 LLM 호출 |
| G2. 구조 기반 (개선 항목) | 파싱한 표 구조와 조문 참조를 그대로 엣지로 씀 (아래 표). 군집은 Louvain 그대로 | LLM 비용 0, 결과가 매번 같음, 누락 원인을 추적하기 쉬움. 이전 실패의 근본 원인을 해결함 | 그래프 **구축** 방식이 논문과 다름 (검색 방식은 같음) |
| G3. 혼합 | G2 골격 위에 G1의 LLM 추출로 개념 엣지 보강 | 가장 풍부함 | 구현량이 가장 많음 |

G2에서 쓰는 엣지:

| 엣지 | 출처 |
|---|---|
| 업종 → 품종 → 해당품목 | 별표 Ⅰ |
| 품목 → 분쟁유형 → 해결기준 행 | 별표 Ⅱ |
| 품목 → 품질보증기간·부품보유기간 | 별표 Ⅲ |
| 품목 → 내용연수 | 별표 Ⅳ |
| 조문 → 개념 | 전자상거래법 조 제목 (예: `제17조(청약철회등)` → 청약철회) |
| 조문 ↔ 조문, 별표 행 → 조문 | 본문의 참조 표현을 정규식으로 추출 (예: `제17조제2항`, `전자상거래법상`) |

질문에서 개념을 추출하는 단계는 어느 안이든 논문과 같이 LLM(gpt-4o-mini)이 맡습니다. 그래프 구축기는 **인터페이스로 분리**해서(DC-7) 나중에 G2·G3로 바꿀 수 있게 합니다.
