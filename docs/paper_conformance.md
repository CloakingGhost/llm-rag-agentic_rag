### 모델을 붙이며 발견한 것

**GPT-5.6 계열은 `temperature=0`을 받지 않습니다.** 기본값(1)만 허용합니다.

```text
BadRequestError: Unsupported value: 'temperature' does not support 0 with this model.
```

그래서 `sampling_args()`로 모델별 분기를 두었습니다. GPT-4o만 `temperature=0`을 쓰고, GPT-5.6 계열은 기본값으로 돕니다. **같은 질문이라도 Luna·Terra는 실행할 때마다 답이 달라질 수 있습니다.** 논문은 이 점을 언급하지 않았습니다.

## 쟁점과 해석

### 쟁점 1. 지연 시간이 논문 기준(10~15초)을 넘는다

Agentic이 Luna에서 39초, Terra에서 17초입니다. 원인은 두 가지입니다.

1. **Critic 재시도**: 3회까지 돌면 생성·검증이 6번 실행됩니다. 논문도 9.2절에서 '과잉 검열' 문제를 인정했습니다.
2. **GPT-5.6의 추론 시간**: Luna는 Vanilla 단독 호출도 11초가 걸립니다. 논문이 가정한 지연 예산은 GPT-4o 기준으로 보입니다.

대응은 IMP-02(Critic 동적 임계치)입니다. 지금은 논문 방식 그대로 둡니다.

### 쟁점 2. 청킹이 논문과 다르다

논문 4.3절은 `chunk size=500, overlap=100`을 씁니다. 그대로 하면 별표의 표가 뭉개져서 경로(`별표Ⅱ > 품목 > 분쟁유형`)라는 개념 자체가 생기지 않습니다. 이전 구현(Notion 기록)이 그 방식이었고, 검색 결과가 개정 이력·부칙 덩어리였습니다.

그래서 **문서 구조를 복원해 행 단위로 자르는 방식**으로 바꿨습니다. 논문의 목적(정확한 조항 검색)은 지키되 수단을 바꾼 경우입니다.

### 쟁점 3. 토큰 42% 절감 (비교 조건을 논문에 맞춤)

논문은 Agentic이 Native보다 토큰을 42% 적게 쓴다고 합니다(부록 B: Native 10,091 → Agentic 5,873).
처음 측정에서는 정반대(Native 3,167 / Agentic 12,904)가 나왔는데, 비교 조건이 두 군데 달랐습니다.

| 조건 | 논문 | 처음 우리 구현 | 지금 |
|---|---|---|---|
| Native가 문서를 넣는 방식 | 정제 없이 **전량 주입** (부록 4-B) | 리랭킹 상위 5개 | **전량 주입으로 맞춤** |
| 질문 구성 | 도메인 밖 질문이 섞인 **100건 평균** | 정책 질의 22건 | **도메인 밖 질문을 섞은 평균** |

둘 다 맞췄습니다.

- `NATIVE_MODE=paper`(기본값)이면 Native는 질의 확장·그래프·리랭킹 없이 벡터 상위 20개를 그대로 넣습니다.
- 대조표 생성기(`uv run python -m cli.compare --ood 6`)가 도메인 밖 질문을 섞고, 정책 질의와 도메인 밖을 나눠 평균 토큰을 냅니다.

#### 다시 측정한 결과 (2026-09-21, Luna, 28문항 = 정책 22 + 도메인 밖 6)

| | Vanilla | Native RAG | Agentic RAG |
|---|---|---|---|
| 전체 평균 토큰 | 1,107 | **2,395** | **9,270** |
| 정책 질의 (22건) | 1,251 | 2,263 | 11,664 |
| 도메인 밖 (6건) | 578 | 2,880 | **494** |

**라우터 효과는 재현됐습니다.** 도메인 밖 6건을 6건 모두 차단했고, 그 구간에서 Agentic은 Native의 **17%**만 씁니다.
Native는 "로또 번호를 뽑아 주세요"에도 법령 문서 20개를 주입합니다(평균 2,880 토큰). 논문이 지적한 그 낭비가 그대로 보입니다.

**그런데 전체 합계로는 여전히 Agentic이 Native보다 287% 많습니다.** 논문의 42% 절감은 재현되지 않습니다. 이유는 두 가지입니다.

1. **우리 Native가 논문보다 4.5배 싸다.** 주입 정책은 같지만(20청크 전량) 청크가 표의 한 행이라 평균 2,263 토큰입니다.
   논문은 500자 청크라 같은 수를 넣어도 10,091 토큰이 됩니다. 쟁점 2(청킹)의 파급 효과입니다.
2. **우리 Agentic은 Critic 재시도가 잦다.** 정책 질의 22건 중 1회 통과는 9건뿐이고, 2회 6건·3회 7건입니다.
   3회까지 간 뒤 폴백한 4건은 평균 16,846 토큰을 씁니다(통과 18건은 10,512).

논문의 Native 수치(10,091)를 기준으로 놓아도 우리 Agentic(11,664)은 16% 초과입니다.
즉 **청크 크기를 맞춰도 42% 절감은 나오지 않고, 남는 차이는 과잉 검열(논문 9.2절)의 재현 강도**입니다. 대응은 IMP-02입니다.

### 쟁점 4. 도구 호출(Lightweight ReAct)과 가상 고객 DB가 없다

논문 3.5절은 ToolLLM의 계획-실행 철학에 Mock API 스키마를 결합한 Lightweight ReAct를 채택했다고 적습니다.
그런데 4.1절에서 그 모듈을 **최종 평가 전에 스스로 껐습니다**.

> "초기 기획에서는 사용자 프로필 조회와 외부 API 호출 모듈을 포함하였으나, 예비 테스트 과정에서 가상 데이터베이스와
> 실제 한국소비자원 Q&A 데이터셋 간의 맥락 및 도구 스키마 불일치로 인하여 유의미한 성능 저하와 환각 현상이 발생하였다.
> 이에 따라 최종 평가는 외부 도구 호출을 배제하고…" (논문 4.1)

9.2절에도 "일반 법률 질의를 주문 처리 요청으로 오분류해 가상 DB를 조회하고, 내역이 없다며 오답을 반환"이 적혀 있습니다.
따라서 **도구가 없는 지금 구성이 논문의 최종 평가 구성과 같습니다.** 남은 차이는 부록 2-B의 라우터가 3분기라는 점뿐이고,
이는 IMP-13으로 뺐습니다. 공개 제품에는 주문 DB가 없으므로 기본은 꺼 둡니다.

## 정리

| 구분 | 건수 |
|---|---|
| 일치 | 15 |
| 일치(변형) — 목적은 지키고 수단이 다름 | 1 (청킹) |
| 불일치 | 3 (지연 시간, 4o-mini 역할 분리 제외, 라우터 3분기) |
| 범위 밖 — 논문이 스스로 제외했거나 이번 제품 범위 밖 | 4 |
| 판정 보류 — 품질 점수를 측정하지 않아 확인 불가 | 3 |

**구조는 논문을 따릅니다.** 세션 메모리 → 라우터 → 하이브리드 검색 → RRF → 리랭킹 → 생성 → Critic → 재시도/폴백의 흐름과 각 노드의 스키마가 논문 서술과 맞습니다.

**다른 점 세 가지는 모두 이유가 분명합니다.** 청킹은 논문 방식으로는 표가 깨져서, 모델 역할 분리는 사용자 지시로, 라우터 3분기는 도구를 쓰지 않기 때문입니다(논문 최종 평가도 같습니다).

**7.2절의 세 발견은 아직 판정할 수 없습니다.** 품질 점수(L2)를 측정해야 하는데 자동 평가를 범위에서 뺐기 때문입니다. 오프라인 평가(IMP-08)를 붙이면 판정할 수 있습니다.
