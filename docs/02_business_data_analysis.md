## 2차에서 바뀐 1차 결정 (개정 4)

| 항목 | 이전 | 변경 |
|---|---|---|
| 자동 평가 (RAGAS, LLM-as-a-Judge, DSPy) | 논문 L1~L3를 품질 KPI로 사용 | **제외.** 채점 비용과 지연이 사용자 키로 청구되기 때문. 저장된 로그로 나중에 오프라인 평가를 할 수 있게 남겨 둠 (IMP-08) |
| CSV 표준답변 | 평가 데이터 1,332건 | **제품에 넣지 않음.** 운영자가 질문을 복사해 넣고 CSV 답변과 직접 비교하는 수동 테스트 자료 |
| CSV 일괄 실행 | 검토 | 제외. 로그에는 실제 사용자 입력만 쌓임 (IMP-09) |

Self-RAG Critic, Intent Router, LLM Re-ranker는 **평가기가 아니라 Agentic 챗봇의 구성 요소**이므로 그대로 유지합니다.

## 2-1. 업무 흐름 정의

| # | 흐름 | 행위자 | 실행 방식 | 단계 |
|---|---|---|---|---|
| W1 | 지식베이스 구축 | 운영자 | **CLI 수동 실행** [결정], 운영자 키 | 원문 로드 → 별표 규칙 파싱 → 자동 검증(V1~V6) → 실패한 표만 LLM 보정 → 재검증 → 청킹 → 임베딩 → 그래프 구축(개념 추출 + Louvain) → 빌드 저장 → 활성 빌드 교체 |
| W2 | 단일 챗봇 질의 | 일반 사용자 | 웹·모바일, 본인 키 | 키 입력(최초 1회) → 모드 선택(`vanilla`/`RAG`/`Agentic`) → 질문 → 실행(단계 표시) → 답변과 처리 과정 → 로그 저장 |
| W3 | 전체 파이프라인 보기 | 일반 사용자 | 웹·모바일, 본인 키 | 키 입력 → 질문 → 3개 동시 실행 → **끝나는 순서대로** 표시 → 로그 저장(요청 1건에 실행 3건) |
| W4 | 대시보드 조회 | 누구나 | 웹 | 파이프라인별 지연·토큰·비용·경로 분포 조회 |
| W5 | 로그 확인 | 운영자 | 웹, `admin`/`admin` 로그인 | 목록·상세 조회, 필터·검색, **같은 질문의 3개 파이프라인 결과 비교** [결정] |

**W1 재실행 조건**: 법령이나 고시가 개정되면 운영자가 `ref/`의 원문 파일을 바꾸고 W1을 다시 실행합니다.

**운영자의 수동 테스트 (제품 밖)**: CSV에서 질문을 복사해 W2·W3에 넣고, 결과를 CSV 답변과 눈으로 비교합니다. 제품에 별도 기능은 없습니다.

### 운영 데이터 (W2·W3가 생성)

**대화 (conversation)**: 같은 맥락으로 이어지는 질문들의 묶음 (논문 3.4 세션 메모리)

| 필드 | 설명 |
|---|---|
| conversation_id | 첫 질문 때 서버가 발급. 화면이 다음 질문에 실어 보낸다 |
| client_id | 익명 브라우저 ID |
| created_at / last_turn_at | |
| turn_count | 이 대화에서 주고받은 질문 수 |
| product_name / dispute_type | **마지막으로 추적된 분쟁 대상 스냅샷.** 로그 표시용이며, 다음 턴 추론에 쓰이는 실제 상태는 서버 메모리에 있다 |
| model | |
| closed | 사용자가 '새 대화'를 눌렀는지 |

**요청 (request)**: 사용자가 질문을 1번 보낸 단위

| 필드 | 설명 |
|---|---|
| request_id | |
| created_at | |
| conversation_id | 어느 대화에 속하는지 |
| turn_index | 그 대화에서 몇 번째 질문인지 |
| mode | `all` / `vanilla` / `rag` / `agentic` |
| question | **질문 원문** |
| client_id | 익명 브라우저 ID. IP는 저장하지 않음 [결정] |
| build_id | 답변에 쓴 지식베이스 빌드 [기본값] |
| status | 2-3 참조 |

**실행 (run)**: 파이프라인 1개가 1번 실행된 단위. W2는 요청당 1건, W3는 3건

| 필드 | 설명 |
|---|---|
| run_id, request_id | |
| pipeline | `vanilla` / `native` / `agentic` |
| status, outcome | 2-3 참조 |
| answer | 최종 답변 |
| route | `policy_inquiry` / `out_of_domain` (Agentic만) |
| fallback_used, fallback_source_run_id | 폴백 여부. W3에서 동시 실행 중인 Native 결과를 재사용했으면 그 run_id |
| critic_attempts | Critic 판정 횟수 (최대 3) |
| no_info_flag | Native 답변이 '정보 없음' 유형인지. 문구 패턴으로 **추정** [기본값] |
| error_type, error_message | 키 무효 / 한도 초과 / 시간 초과 / 취소 / 기타 |
| started_at, ended_at, latency_ms | |
| tokens_in, tokens_out, cost_usd | 비용 = 토큰 × 설정 파일 단가 [기본값] |
| model | `gpt-4o-mini` |

**처리 단계 (step)**: 실행 안의 노드 1회 수행 단위

| 필드 | 설명 |
|---|---|
| step_id, run_id, seq | |
| node | `memory` / `router` / `retrieve` / `rerank` / `generate` / `critic` / `reject` / `fallback` |
| attempt | 재시도 회차 (1~3) |
| latency_ms, tokens_in, tokens_out | 대시보드의 노드별 소요 시간 |
| output | 노드별 결과 JSON. 예: router `{route, reason}`, memory `{dispute_target}`, retrieve `{query}`, critic `{feedback, is_grounded, is_relevant, is_complete}` |

**검색 결과 (retrieved_chunk)**: retrieve·rerank 단계의 청크

| 필드 | 설명 |
|---|---|
| step_id, chunk_id | |
| path, **text_snapshot** | 청크 **원문 스냅샷** [기본값]. 지식베이스를 다시 구축해도 로그가 당시 근거를 그대로 보여주게 하기 위함 (DC-10) |
| vector_score, graph_hit, rrf_score, rerank_rank | 어느 경로로 왔고 몇 위였는지 |
| selected | 최종 상위 5개에 들어 LLM에 전달됐는지 |

## 2-3. 상태 정의

### 실행 (run)

| 파이프라인 | 진행 상태 (화면에 단계로 표시) |
|---|---|
| Vanilla | 대기 → 생성 → 종료 |
| Native RAG | 대기 → 검색 → 생성 → 종료 |
| Agentic RAG | 아래 그림 |

```text
[대기] → [라우팅] ──도메인 밖──▶ 종료: 거절
            │
         정책 문의
            ▼
     [분쟁대상 추출] → [검색 n/3] → [생성] → [검증] ──통과──▶ 종료: 답변
                          ▲           ▲         │
                          └─재검색─────┴─재생성──┤  (1회차 실패 → 재검색, 2회차 실패 → 재생성)
                                                └─3회 초과──▶ [폴백] ──▶ 종료: 폴백 답변
어느 단계에서든:  오류 ──▶ 종료: 실패   /   중지 버튼 ──▶ 종료: 취소   /   60초 경과 ──▶ 종료: 실패(시간 초과)
```

**종료 결과 (outcome)**

| outcome | 의미 | 화면 |
|---|---|---|
| `answered` | 정상 답변 | 답변 + 처리 과정 |
| `rejected` | 도메인 밖 거절 (Agentic) | 고정 거절 문구 |
| `fallback` | Critic 3회 초과 후 Native 결과 사용 | 답변 + '폴백됨' 표시 |
| `failed` | 오류. error_type = 키 무효 / 한도 초과 / 시간 초과 / 기타 | 오류 안내. 키 무효면 키 재입력 안내 |
| `canceled` | 사용자가 중지 [결정] | '중지됨'. 그때까지 쓴 토큰·비용은 로그에 남음 |

**규칙**

| 항목 | 규칙 |
|---|---|
| 진행 표시 | **진행도는 표시하지 않음** [결정, 5차 검수에서 변경]. 실행 중에는 로딩 표시만 두고, 단계 이름·회차는 보여주지 않음. 처리 과정은 완료 후 트레이스에서 확인. 답변은 스트리밍하지 않고 확정된 뒤 한 번에 표시 |
| 시간 초과 | 실행 1건당 **60초** [결정], 설정 파일로 변경 가능. 폴백 시간도 포함 |
| 중지 | **요청 단위** [기본값]. 병렬 모드에서 누르면 진행 중인 실행 3개가 모두 중지됨. 이미 끝난 실행은 그대로 둠. 중지되면 폴백하지 않음 |
| 폴백 실행 | W3: 동시에 실행 중인 Native 결과를 재사용해서 추가 비용이 없음 (Native가 끝날 때까지 기다림). W2: Native를 새로 실행 [기본값] |
| 병렬 모드 부분 실패 | 실패한 파이프라인 칸에만 오류를 표시하고 나머지는 계속 진행 [기본값] |

### 요청 (request)

| 상태 | 조건 |
|---|---|
| `running` | 종료되지 않은 실행이 있음 |
| `completed` | 모든 실행이 `answered` / `rejected` / `fallback` |
| `partial` | W3에서 일부 실행만 `failed` |
| `failed` | 모든 실행이 `failed` |
| `canceled` | 사용자가 중지함 |

### 지식베이스 (W1)

| 대상 | 상태 흐름 |
|---|---|
| 별표 표 | 파싱됨 → 검증 통과 / 검증 실패 → LLM 보정 → 재검증 통과 / 재검증 실패 → **표 통째 청크** (실패 목록에 기록) |
| 빌드 | 진행 중 → 완료 → **활성** / 실패. 완료된 빌드로만 교체하고, 실패하면 이전 활성 빌드를 계속 씀 [기본값] |

### 브라우저·관리자

| 대상 | 상태 흐름 |
|---|---|
| API 키 | 미입력 → 확인 중 → 유효 / 무효. **입력 즉시 검증**(비용 없는 모델 목록 조회) [기본값]. 실행 중 키 무효 오류가 나면 무효로 전환 |
| 관리자 | 로그아웃 ↔ 로그인 (`admin`/`admin`). 로그인해야 W5 로그 화면에 접근 가능 |
